## Review round 1 (GPT-6.1 Sol)

Merged `t3/streaming-reveal` at `da17e8c` first, with that branch's round. The merge also points
`.agents/tools/streaming-parse-bench.test.ts` at `ReplyMarkdown`, since this branch renamed
`LiveMarkdown` and left the benchmark importing a name that no longer exists.

5. Rows were keyed `reply:N` by place, so a change in which rows show handed one reply's node and
   state to another. Each row now keys by its own identity (`src/app/reply-keys.ts`): a saved row
   or progress line by its ID, the live row by `live:N`, new for each live reply. Each turn's view
   keeps a record of the rows it committed last. A saved row takes the live row's key only when one
   update shows the hand-off: the live row is gone, or shows text that does not continue it, and
   exactly one new row appeared, a saved assistant row whose text continues the live row's.
   Anything else renders the saved row under its own ID, in a new node, as on `main`. The record
   holds the last commit's row IDs, the live row's key and text, and one entry per handed-on
   reply, dropped once that reply leaves the turn. It goes with the turn's view, so switching chats
   or the turn leaving the window drops it.
6. A reply that streamed and was saved could render differently from the same reply opened fresh.
   `streamingBlocks` now splits lines at `\r\n`, `\r` and `\n` and cuts each block from the text,
   so its line endings stay as they arrived. A blank line is one of only spaces and tabs, so a
   no-break space is text. A closing fence may be followed only by spaces and tabs. On the saved
   path, `ReplyMarkdown` keeps the blocks only when `blocksAgree` finds that they parse to the same
   Markdown tree as the whole reply, positions aside. It uses the same parser and GFM extensions
   React Markdown uses, already direct dependencies. Otherwise the reply parses whole in the same
   container.
7. The block comparator is `sameBlock`, exported and tested on its own.

The README no longer claims a selection always survives. It names the cases that build the row
again: more than one new row at once, a steer or another member's message starting a new turn,
and blocks that disagree with the whole parse.

`.agents/tools/streaming-preview.ts` gained `ANSWER_PARAGRAPHS`.

2. A new live reply that began like the previous one inherited its node and selection, and the
   saved original got a fresh node, because the live row kept its key while its text continued.
3. A progress line that continued the live text took the live reply's node and selection.

   The rule, now stated in this order at the top of `src/app/reply-keys.ts` and read the same way
   in the code: a progress line never takes a live key; whenever an update adds a saved assistant
   row, the live reply after it gets a new live key, whatever its text; the saved row takes the old
   live key only when it is the one new row, a saved assistant row that is not a progress line, and
   its text continues the old live text; anything else keys each row by its own identity and builds
   it again. "The one new row" is read strictly: a saved reply that lands beside a progress line is
   still built again, as round 1 cleared.
4. The saved-path check is bounded. `MAX_CHECKED_REPLY` is 25,000 characters; a longer saved reply
   parses whole in the same row, as `main` does when it builds the row again, and a selection in it
