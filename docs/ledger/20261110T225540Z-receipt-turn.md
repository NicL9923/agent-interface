# November 10 the admission's turn on a receipt and the early thinking row

## What changed

- `receipt()` (`src/server/hermes-mapping.ts`) keeps the add-on's `turn` on an accepted new task: `queued`, `joined`,
  `none` or `unknown`, any other value `unknown`. A missing one is `started` only from an add-on whose capabilities
  report `admission_turn` (`Contract.admissionTurn`, reset on disconnect). Older add-ons, lookups, steers and receipts
  that are not accepted carry none.
- An accepted admission answer also carries `admittedVersion`, the assistant's structural version taken when the
  answer reaches `hermes.ts`. A conversation read's version is the structural generation when it was asked, so a read
  with a newer version was asked after the answer arrived, and the add-on answers only after its final journal
  transaction, which ends the admission for reads (`SHOWN_RUN`, `admitting`).
- `GET /submissions/:id` answers a lookup, which never carries `turn`; it now adds the recorded receipt's `turn` and
  `admittedVersion` while both say `accepted`.
- `SendTimings.admitted` takes the turn: `queued`, `none` and `unknown` log at once, `ended: "not-started"`;
  `joined` is measured as a steer, `steered: true`.
- `src/app/sent-echo.ts`: `none` drops the echo and its row at acceptance, and the composer shows the receipt's
  message; `joined` adds no row, like `steered`; with `started`, `settledHere` takes a settled report as this turn's
  only from a read newer than `admittedVersion`, and the copy-version rule stays for everything else.

## The remainder, closed

Sequence that failed before, for a message sent after a failed turn: reads R1 (`boot:0:5`) and R2 (`boot:0:6`) are
both asked while Hermes admits the message, so both show the copy and the last turn's `failed`. The answer arrives at
`boot:0:7`. R1 brings the copy; R2 is newer than R1, so the old rule ended the row on R2 and put the last failure's
Retry on the new message. Now R2 is not newer than `boot:0:7`, so it keeps thinking; R3 at `boot:0:8` was asked after
admission and shows this turn's outcome. A read at `boot:0:7` itself may have been asked just before the answer, so
it does not count either. What still falls back to the old rule: `queued`, `unknown`, an older add-on, a receipt
recovered by lookup, and a read from another server process, whose version never compares.

## A typed stop keeps the draft (Grok 4.7 review of `ce1e2a9`, P2)

`origin/main` (`145104f`, the squash of #327) merged as `226bc3b`. Its tree is `ce1e2a9`'s: main's tree equals
`b0340a0`, so each of the four conflicts took this branch's side, and `git diff ce1e2a9 226bc3b` is empty.

An accepted receipt with `turn: "none"` sent nothing to the assistant, yet it emptied the draft everywhere. Now:

- `SubmissionRepository.receipt` skips `clearSubmittedDraft` for it, so the draft, its files and its revision stay,
  and no `draft` event reaches other devices. Any other turn, an `unknown` one or none from an older add-on, clears
  as before, and so does a typed stop whose answer was lost and recovered by lookup, which carries no turn.
- `withAdmission` moved from the conversation routes to `store-submissions.ts`. Talk's `refresh` uses it, because a
  lookup replaced the admitted receipt and dropped its `turn`, which alone sent a typed stop down the missing wait.
- `talkAnswer` answers `none` with `refused` and the receipt's message at once.
- Web: `useSubmission` treats it like a refusal on the send's answer and on a receipt check: the echo goes, the
  draft keeps or regains its words and files, no longer marked as sent. The decline's question stays, and a turn
  retry answered `none` reads as not taken, with Hermes's message.

Not changed: participation (the receipt's run ID is its request ID, and no run with it ever exists), the timing
log (already `not-started`), the add-on (it unstages the send's images and keeps the interruption review), the read
position and notifications (neither reads receipts), and iOS, which still clears its local copy on every accepted
receipt (`ios/AgentInterface/AppStore+Sending.swift:109`).
