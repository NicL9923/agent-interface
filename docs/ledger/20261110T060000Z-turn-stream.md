# November 10 turn events keep a reply streaming across tools

Branch `t3/turn-stream`, from `origin/main` at `2d461e3`. Checks ran on NicolasLaptop (Linux x86_64,
Node 24.22.2). No real Hermes, iOS build or deployment ran, so no production number exists yet.

## What changed

- `?inflight=3` streams: after each structural frame the Hermes runtime reads the running turn itself,
  once per assistant, one read on its way and one queued, only while such a stream is open. The read is
  windowed from the turn's first message (`turnStarts`). Each whole live reply goes as `event: turn`
  with the turn's saved messages, decorated by `shownMessages` (`src/server/conversation-view.ts`),
  which the conversation read now uses too. Growth stays `inflight-delta`.
- Every conversation read and turn event carries `version`, `BOOT:EPOCH:GENERATION`. The web client
  shows a live reply only beside messages of its own version, puts a newer held turn on top of an
  older read, and ignores an older turn.
- A turn read waits for client reads asked at the current structural generation. Round 1 also made a
  client read wait for a turn read on its way; round 2 removed that (see below).
- On a turn stream, a live tick that finds nothing to send gives its 250 ms window back. Round 1 did this
  for every mode; round 2 limited it to `?inflight=3`.
- `src/server/conversation-view.ts` joined `src/shared/qualification-inputs.json`: it reads runtime
  messages. This branch also changes `hermes.ts` and `conversation-routes.ts`, so the host needs a new
  qualification receipt either way.

## Measurement

`MEASURE=1 npx vitest run tests/live-turn-timing.test.ts --silent=false`: the real app and Hermes
runtime, a fake socket whose opens take 60 ms of virtual time, a client that refetches on each change
notice, a real send, then text, tools and text, then the turn ends. Time from each structural frame (and
the token sent with it) to that token reaching the client, by a live event or a read. Opens count every
Hermes open from the send through the client's reads after the turn ended:

| | `message.start` | tool 1 done | tool 2 done | opens, 2 tools | opens, 10 tools |
| --- | --- | --- | --- | --- | --- |
| `origin/main` 2d461e3, `?inflight=2` | 105 ms | 445 ms | 745 ms | 6 | 14 |
| this branch, `?inflight=3` | 61 ms | 61 ms | 61 ms | 10 | 26 |

Corrected in round 2. Round 1's open counts, 6 and 13 against 9 and 24, stopped while the turn was still
running and covered that interval only. The test now ends the turn before counting and asserts every
figure in this table, for both modes. The main row ran in a detached worktree of `2d461e3` with the same
test and helper copied in, twice, same numbers. The `?inflight=2` row on this branch matches main. The
measuring step is 5 ms.

What it measures: a token reaching a scripted socket client under a fixed fake read time. It does not
measure rendering. The fake answers overlapping opens, where the real add-on serves one assistant's
opens one at a time. Lock contention, a larger read, a client read the turn read must wait for, or a
live-event tick not yet due can each shrink the gain.

# Round 2: review findings

GPT-6.1 Sol reviewed `efbb330` and verified three findings with failing tests against the real app and
runtime. Fixed on `fix/turn-stream-review`, pushed to `t3/turn-stream`. NicolasLaptop, Node 24.22.2.

## 1. P1: mode 3 made `?inflight=1` and `?inflight=2` clients lose saved text

The server's own turn read replaced the snapshot every live reply is built on and notified every watcher,
so a mode 1 or 2 stream beside a mode 3 stream got a whole `inflight` holding only "Found it." before its
throttled change notice and read, and "Looking." disappeared.

Separation (`src/server/hermes.ts`, `src/server/conversation-routes.ts`):

- Two snapshot stores. `snapshots` serves modes 1 and 2 through `inflight()`, and only a client's
  conversation read stores it, as on main. `turnSnapshots` serves mode 3 through the new `turn()`, and
  client reads and turn reads both store it. A structural frame or a disconnect clears both.
- Its own channel. `followTurns(botId, restored)` calls only the following mode 3 streams when a turn read
  lands. Watchers, `talk.ts` and the change-generation counter never hear it. Round 1 used
  `changed(botId, "inflight")`, which reached every watcher.
- An observing open. A turn read's open neither records itself as applied, so it never supersedes a
  client's open, nor touches live state (session ownership, the opening count, requests, activity, text,
  reasoning, tools). It never starts the settle timer. So client reads no longer wait for turn reads.
- The route restores main's legacy tick: an empty tick spends its window on modes 1 and 2.

## 2. P2: a read from before a restart could undo a newer turn

A read begun on boot A and answered after a boot B turn event replaced B's rows. Its version did not
compare with B's, so it was taken as the latest.

Rule settled (`src/app/use-conversation.ts`, `docs/native-api.md`): the view follows one boot at a time.

- When a read or turn event from a new boot is taken, the followed boot is retired. Anything later
  carrying a retired boot is dropped: a read is read again, a turn event is ignored.
- A read asked before the view followed its current boot, answered by another boot, is read again.
- A read asked after it, answered by an unretired boot, is newer and followed.
- The first turn event from a new boot is never placed on another boot's conversation. It is held, the
  view reads again, and it goes on top of that read if newer. Until then the old view stays, without the new
  live reply.

The docs' "whichever arrived last" rule is replaced.

## 3. P2: a segment saved before a steer showed twice

Present on main too. The snapshot that strips saved text from the live reply started at the last user
row, which after a steer is the steered guidance, so segments saved before it were not stripped.

`turnStart` in `src/server/hermes-mapping.ts` is now the one turn boundary: the last prompt that is not
steered guidance, or steered guidance only when no other prompt is there. `turnRows`, the snapshot's rows
and `inflightMessage` all start there. This changes what modes 1 and 2 send, and what the conversation
read's live tail holds, but only after a steer saved inside a running turn. There it removes the
repeated segment, a correction of visible duplication on main. Each mode has a test.

# Round 3: two regressions from round 2

GPT-6.1 Sol's second review cleared modes 1 and 2, privacy, the in-place steer fix and the measurements, and
verified two regressions from `b1c6efe`: its reproductions pass at `efbb330` and fail at `1e00534`. Fixed on
`fix/turn-stream-r2`, pushed to `t3/turn-stream`. NicolasLaptop, Node 24.22.2. Each finding's tests were written
first and watched failing.

## 1. P2: a delayed event from an intermediate boot froze the view and looped on reads

The view followed boot A, boot B opened the stream, a read from boot C landed, then B's buffered first turn arrived.
Round 2's rule let that event retire C, so every later C read was dropped and read again at once.

Rule now (`src/app/use-conversation.ts`, `docs/native-api.md`): only a read the view asked for decides which boot it
shows, and the newest read asked wins, whichever boot answers it.

- The answer to the most recent read asked is taken, and its boot becomes the view's.
- An older read's answer from another boot than the view's is dropped. The newer read is already asked, so dropping
  asks nothing. One from the view's own boot is taken and ordered by version, as before.
- A turn event from another boot never changes the view's boot. It is held and asks one read, which later such events
  share. The first read taken that was asked after it settles it: on top when that read is from its boot and older,
  dropped otherwise. A failed read leaves it held for the next read taken.

Bound: a response never asks for a read because of the boot that answered it. Every read answers an input: the opening,
a change notice, a reconnect, wake or poll, the person's navigation, growth that does not continue the reply held, a
turn that cannot be placed, or one held turn event at a time. Asks made while a read is on its way become one read. The
only read a response asks for itself is the cached-page correction, once. Two boots that disagree cost one read per
change notice and one per held turn event; the ten-round test pins 20 reads for 10 rounds.

Round 1's two orders still hold under the new rule, with their tests: rows lost with growth suppressed (a read the old
boot answered landing after the new boot's turn), and a finished reply going back to thinking.

## 2. P2: queued guidance repeated saved text in every mode

Round 2's `turnStart` guessed the turn's start from the rows' steering flag. Guidance Hermes queued instead of steering
in still carries `app_steering`, so the boundary landed on the original prompt, and the guidance turn's saved
"Loft checked." showed again in the live "Loft checked. Dry.", in modes 1, 2 and 3 and the read's live row.

What identifies the native turn's start, checked in Hermes upstream at `ed1afb0` (a local clone, not the production
host): `tui_gateway/session_history.py` `_start_inflight_turn` sets `inflight_turn.user` to the prompt and clears the
live text whenever a native turn starts, including a queued prompt drained after the turn (`prompt_turn.py`,
`session_auto_continue._drain_queued_prompt`) and a steer left over at turn end and requeued as a prompt
(`_run_post_turn_followups`). A steer consumed in place goes through `_record_inflight_correction`, which appends to
`corrections` and never writes `user`. So `inflight.user` is the original prompt after an in-place steer and the
guidance after queued guidance starts its turn. Between native turns Hermes clears the snapshot and the app clears its
live text on `message.complete`, so no prompt is reported only when there is no live text to strip. The add-on
(`src/hermes/extension.py`) passes `inflight` through untouched apart from adding exposed reasoning, and its own
tests never set `inflight.user` for a steer; they cover only an interrupted turn's snapshot.

Boundary now (`src/server/hermes-mapping.ts`): `turnStart(rows, prompt)` is the last user row whose text is
`inflight.user` without its file references. `turnRows`, the snapshot's rows for modes 1 and 2, and
`inflightMessage`'s stripping all use it. A prompt Hermes names but has not saved yet strips nothing, since none of
the saved rows are its turn's. With no prompt reported, the last prompt, as on `main`.

For queued guidance a turn event's `messages` start at the guidance prompt. The first such event, from a turn read
windowed from the earlier turn's prompt, names the earlier turn's last row as `after`. Later ones are windowed from
the guidance and carry no `after`. The client keeps everything before the guidance, which holds the earlier native
turn as it already showed it: that turn ended before the guidance started, so its rows no longer change. A client that
holds neither the guidance nor `after` reads, as before.

Modes 1 and 2 against `main`: the only change is the in-place steer's dedupe, where the native prompt is earlier than
the last user row. Everywhere else the boundary is the last user row, as on `main`, or strips nothing for an unsaved
prompt where `main` stripped another native turn's rows.
