# November 10 live updates every 100 ms on the web client's turn stream

Branch `t3/live-tick` over `origin/main` at `caeeb7f`, on NicolasLaptop (Fedora 44, Linux x64, 32 cores),
Node 24.22.2, Chromium from Playwright's bundled build. Server and web client changed; no iOS, Python or
Hermes code changed. `src/server/conversation-routes.ts` and `src/server/event-stream.ts` are qualification
inputs (`src/shared/qualification-inputs.json`), so the next release needs a new Hermes qualification.

## Change

- `?inflight=3` turn streams, the web client's, send live growth at most every 100 ms (`TURN_TICK_MS`).
  `?inflight=1` and `?inflight=2` keep 250 ms (`LIVE_TICK_MS`). Both are named constants in
  `src/server/conversation-routes.ts`, with the numbers below in their comments. No configuration.
- A `turn` event from the server's own read after a structural change goes at once instead of at the next
  tick, so a finished turn's saved reply is not held back. Before, it waited up to the rest of the tick.
- A stream whose client has not read what was written, past the socket's buffer, gets no live update until
  the response drains (`EventStream.writable` in `src/server/event-stream.ts`). The update after the drain
  carries everything since the last one the client got, because `sent` is left as it was. Before, every tick
  wrote whatever the client had not read, without bound: a stalled client let 17.8 MB queue in the test below.
- `CATCH_UP_MS` stays 300. Its comment now gives the measured reason.

## What runs and how often

Each stream owns its own `setTimeout`, armed only by a growth notice (`notice("inflight")`), so one timer
wakeup per stream per update and none while nothing streams. Measured below: 0 wakeups a second with 10
streams open and nothing streaming, in every mode, before and after.

bursty 233 / 341 / 381, paint gaps unchanged, no long tasks.

How the 300 ms catch-up meets a 100 ms tick: each update speeds the reveal up to clear its backlog within
`CATCH_UP_MS`, so at a steady rate the reveal holds about 300 ms of text and still moves when the next update
lands. The queue never ran dry at 150 characters a second, the paints stayed 33 ms apart, and on bursty input
the reveal was steadier than at 250 (paint gap p95 83 ms against 134 to 149). A shorter catch-up cut another
60 to 90 ms, but on bursty input the reveal ran out between bursts more often: paint gap p95 201 ms at 200
and 333 ms at 150. So `CATCH_UP_MS` stays 300; that is the only setting changed by measurement here.

reviewer: ready, with no P1, P2 or P3 finding.

- It captured the streams from the real Fastify app on `origin/main` and on this branch for the same scripted reply.
  Modes 1 and 2 matched event for event at the same fake times, including mode 2's deltas, and a turn ending inside
  the tick on both. Mode 3 differed only by the 100 ms grid and by the saved turn arriving at once.
- With a paused client and 20 growths of 512 KB, mode 2 and mode 3 peaked at 524,483 bytes queued and mode 1 at
  2,097,326, and each resumed stream ended on the exact reply with no base mismatch. A segment change while the
  socket was full resumed as a whole turn. A slow stream beside a fast one caught up in fewer, larger deltas. Thirty
  structural notices against a full socket added 19 bytes.
- The drain signal is Node's `writableNeedDrain` per response. In front of a proxy it means the proxy's TCP stack took
  the bytes, so bytes held in the proxy and the kernel are extra and stay bounded only while the proxy stops reading
  when the browser does. It did not run Caddy.
- Nothing in the web client is keyed to a 250 ms tick. One timer per stream, armed only by growth.
- All six of its mutations went red.
- On the measurements: it read both tools and did not run them. A constant network round trip shifts both intervals
  alike, so the 40 to 70 ms gain can survive it; the absolute 230 to 264 ms does not carry over from loopback.
