## Native behavior relied on, read from upstream `ed1afb082eb3`

Read in a scratch clone of `NousResearch/hermes-agent` at the production revision.

- `messages.id` is `INTEGER PRIMARY KEY AUTOINCREMENT` (`hermes_state_common.py:532`), so an ID is never
  reused and every new row takes a higher one.
- No writer changes a stored `message_uid` except to fill a NULL with a fresh random one: the insert
  trigger (`hermes_state_common.py:815`) and the legacy backfill (`hermes_state_schema.py:1161`).
  Transcript repair lists `message_uid` among the columns a rewrite never touches
  (`agent/transcript_repair.py:20-26`); the prune keeps it through `{**original, "content": ...}` and
  stores its archived twin under a new, higher ID (`hermes_state_prune_rewrite.py:237-248`).
- Deletes remove a whole session's rows, or all its active ones (`hermes_state_messages.py:774`,
  `:1951`, `hermes_state_sessions.py`), so a visible row never outlives its original.
- The proactive prune rewrites a tool row's content in place under the same ID
  (`hermes_state_prune_rewrite.py:133-160`, `:248`). Tool content is therefore not keyed by row ID alone.
- `project_compaction_message_for_display` returns `message.copy()` for any row that is not a
  compaction summary (`agent/compaction_display.py:33-43`); no redaction applies to tool output there.
- Native activation rebinds the session to the transport bound on the calling thread
  (`tui_gateway/methods_session.py:1162`); the add-on's own activation runs synchronously on its thread.

Conclusion, withdrawn in review round 2 for restores: once a row is readable through the store, the earliest row with its `message_uid` in that
stored session is final, so the add-on keeps only rows the lookup found and asks again about any it
could not read yet. That case is real: Hermes stamps `_row_id` on the history dict inside the write
transaction (`hermes_state_messages.py:685`), and `_execute_write` commits after it returns
(`hermes_state.py:1013`), so another connection can see the ID before the row.

## Review round 1 (GPT-6.1 Sol), November 9

Four findings, each reproduced by the reviewer and confirmed absent on `origin/main`. Fixed on this
branch over `4a2de4e5`. Source fingerprint
`sha256:0b279400738feb0f3c579adcfa1d6c2faaecdf3aad409c1c19038359b62438ce` (1666 files); `src/hermes`
`sha256:e61aef0adff86bda704c7385c3517e3033d01cac85ae7fa56e5c1bfd1fb956fd`.

1. Eviction changed the answer being assembled. `original_rows()` now takes the open's answer from
   `originals` before it inserts anything, so a fill that evicts a hit cannot drop it from that open.
   `tool_records()` already built its answer before inserting, and `tool_result()` answers each row on
   its own, so `originals` was the only table with this shape.
2. A replaced or restored database reused cached identities. Review round 2 found this guard
   insufficient and removed the table it guarded. Hermes's test for a replaced state.db
   (read at upstream `ed1afb082eb3`): the registry retires a generation when the path's
   `(st_dev, st_ino)` changes (`hermes_state_registry.py:195-224`, `stat_db_file_identity` at
   `hermes_state_common.py:338`), and `SessionDB._db_file_was_replaced` also compares the per-file
   generation stamp Hermes writes once into `state_meta` and the header's application_id
   (`hermes_state.py:1180-1247`), because a `cp` onto the path keeps the inode. Neither sees a snapshot
   of the same file restored in place: native `/snapshot restore` and `hermes import` write pages with
   SQLite's backup API into the live inode (`hermes_cli/backup_restore.py:239-290`), and the copy
   carries the same stamp. So `originals` is dropped when the inode or the application_id changes, or
   when the newest row it learned no longer has that row's uid. A snapshot of the same file that still
   holds that row also holds every row below it, because IDs only grow and Hermes deletes only a whole
   session's rows or all its active ones. All three come from one extra read per open. The journal is the add-on's own, with one
   connection for the life of the process: `tool_records` is dropped when that connection's
   `PRAGMA data_version` changes, which only another connection's commit moves. A journal replaced
   by rename is never read until a restart, which starts every cache empty, so an inode check there
   could not change an answer and was left out.
   What can restore either file under a running gateway: Hermes's own restore takes
   `exclusive_maintenance`, which refuses while the gateway owns the profile
   (`gateway/runtime_ownership.py:330-351`). This repo's tools never restore `state.db` or the journal:
   `backup-app.mjs` copies only the app's own database, `prepare-when-idle.py` reads `state.db`
   read-only, and the deploy, guarded deploy, rollback and recovery tools stop or restart the
   gateway. The cases covered are therefore out-of-band ones: a file renamed over `state.db`, another
   database written into it, an older snapshot of it written into it and then written again, and a
   journal snapshot written into the live journal.
3. Callers could corrupt later opens through returned objects. An open now returns copies of the rows
   it returns, after the window has cut them down, so no response shares a dict or list with the row
   cache or the decorated-history cache. Measured against storing immutable dict and list subclasses
   at fill time, and against copying each cached value as it is read (seven interleaved rounds):

   | Code | Open median | Open p90 | Activate | Decorate | Window |
   | --- | --- | --- | --- | --- | --- |
   | `ec24b94` (main) | 82.6 | 88.8 | 20.6 | 59.7 | 0.8 |
   | `4a2de4e5` | 24.9 | 30.3 | 7.3 | 15.7 | 0.8 |
   | Copy on the way out (chosen) | 21.9 | 28.4 | 5.3 | 15.1 | 1.0 |
   | Copy each value as read | 28.1 | 34.0 | 8.9 | 17.5 | 0.8 |
   | Immutable forms | 21.1 | 26.0 | 5.0 | 14.8 | 0.8 |

   Copying the returned rows costs 0.2 ms in the window phase; immutable forms cost nothing measurable.
   Copying won on the rule, not the clock: it leaves no shared object at all, and an in-process caller
   that edits its response keeps working instead of getting a TypeError. A read with no window copies
   every row, 9 ms for 5,000 rows in isolation; the app server always sends a window or omits history.
4. The benchmark did not match Hermes. Its store now has Hermes's `messages` table and all ten indexes on
   it verbatim, archives on compaction as Hermes does, stamps an application_id and exposes `db_path`.
   Its description says what it builds: five-row turns with three tool calls each, 3,000 tool rows in
   5,001. `--plan` prints the plan of each statement the add-on ran. A scratch script read Hermes's own
   `SCHEMA_SQL` and `DEFERRED_INDEX_SQL` out of `hermes_state_common.py` without importing it, built a
   store from them plus the platform index from `hermes_state_schema.py:977`, filled it and the
   benchmark's store with the same transcript, and compared: the `messages` table and its ten indexes
   are identical, and `EXPLAIN QUERY PLAN` is the same for all three lookups on SQLite 3.51.2. The uid
   lookup is `SEARCH messages USING INDEX idx_messages_session_active (session_id=?)` with
   `USE TEMP B-TREE FOR GROUP BY`, where the old benchmark had
   `SEARCH messages USING COVERING INDEX idx_messages_session_uid (session_id=? AND message_uid=?)`.

## Review round 2 (GPT-6.1 Sol), November 9

One finding (P1): the guard over `originals` kept wrong mappings. The reviewer's sequence, now a
committed test with real SQLite and the real backup API: rows 1 to 4 hold uids A, B, C and Z (Alice's
message, then Bob's); a snapshot; compaction copies them to rows 5 to 8 and an open learns 6 -> 2; the
snapshot is restored into the same inode; one row is written and later dropped, and compaction keeps A,
C and Z as rows 6 to 8. Inode, application_id and the newest row (8, Z) are unchanged, so the warm open
labelled Alice's message as Bob's.

Fixed over `0110552` by option 3: the `originals` table is gone, and `original_rows()` asks state.db
about every visible row on every open, as `origin/main` does. `tool_results` and `tool_records`, which
the reviewer cleared, are unchanged. Source fingerprint
`sha256:297662356986cb48a216eec60edd7944b64aafa759a9a754afc6559a9fc3312b` (1666 files); `src/hermes`
`sha256:a87400e8882a2f0f094e52d1a9a7ffd5765faf210fe576ea31fdbfecf1f8e4e0`.

### The three options

1. Keep each mapping with its uid, and reuse it only when the copy and its recorded original both still
   hold that uid in this session. Unsound. The argument needs "no row below the original can come to
   hold the uid", and Hermes breaks it. `replace_messages(active_only=True)` deletes a session's active
   rows and inserts them again from their dicts unless `archive_dropped` is set
   (`hermes_state_messages.py:720-775` at `ed1afb0`), and `stamp_message_uid` keeps a uid the dict
   already carries (`agent/message_metadata.py:164-174`, called from `_insert_message_rows` at
   `hermes_state_messages.py:675`). The gateway's `/retry` does this
   (`gateway/slash_commands_session.py:542`), as do its transcript rewrite
   (`gateway/session_transcript.py:565`) and the ACP adapter (`acp_adapter/session.py:399`). The TUI's
   edit and regenerate pass `archive_dropped=True`, which archives instead (`tui_gateway/methods_prompt.py:572`).
   So in one history Alice's message
   moves from row 1 to row 5, and compaction copies it to row 9; an open learns 9 -> 5. Restore the
   snapshot from before the replace and compact twice: rows 5 and 9 again hold uid A, and row 1 holds it
   too. The check passes and reuses 9 -> 5; a cold open says 1. Keeping the inode, stamp and newest-row
   check as an early exit does not help, because all three are unchanged in that sequence. A sound check
   would have to prove that no lower row holds the uid, and Hermes's only uid index is restricted to
   active rows, so that is the same session scan as no cache. Within one history the old argument still
   holds: IDs only grow, and a delete removes a visible copy along with its active original. A restore
   is what breaks it, because row IDs repeat across histories.
2. Drop `originals` whenever the state.db or WAL signature changes. Sound in practice: it asks again after
   any change to either file's inode, size, mtime or ctime. During a turn every open follows a commit, so
   it emptied the table before every measured open and cost two more `stat` calls. That makes it slower than
   option 3 and no better.
3. No `originals` table. Chosen: sound by construction, and faster than option 2. Option 1 was 5.6 ms
   faster at the median, above the 3 ms bar, but the bar applies only to a sound option.

### Benchmark change, made before measuring

The store now runs in WAL mode, as Hermes opens state.db (`hermes_state_wal.py:254`). Before, it used a
rollback journal, so no WAL existed, although the database file's own signature still changed on every
commit. It already committed one tool row before each open. Each run now refuses to report if that
commit left the WAL unchanged or if an open skipped `original_rows`. It times `original_rows` on its own
and prints p90 for every phase.
