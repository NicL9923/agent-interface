## Item 1, #460: what could be written under the new member's token

The red run held member two's bootstrap read and, in that gap, did what the app allows there: Retry in Settings, a draft flush as a typing pause or leaving the app does, a queued upload, Retry on the unconfirmed send, and the reading position. On `af8d1c38` all five went out under member two's token (`red.log`, `/Volumes/DevSSD/scratch/followups-ios/red-results/ios-test-20261121T024603Z-99616.xcresult`):

`PUT /api/bots/bot/draft`, `PATCH /api/preferences` with member one's `"theme":"dark"`, `POST /api/bots/bot/uploads`, `POST /api/bots/bot/messages`, `PUT /api/bots/bot/read-position`.

The draft save also has a path with no tap: a save that failed while the session was expiring schedules a retry that checks only `generation`, which did not change until the bootstrap read answered.

Questions the task asked, checked against the code:

- `persistDraft` at the switch writes the open draft under member one's scope. `scope` comes from `bootstrap.user.id`, which is still member one's until `resetAccountContent` clears it. The test reads member one's key after the switch.
- A request already in flight keeps the token it was built with. `APIClient.exchange` sends a request again on the primary origin only while `token == sentToken`. Store-level retries for drafts, uploads and the preferences queue check `generation`, which the switch changes before the token goes in.
- No other path installs a token for a different member. Renewal keeps the same token. A restored session reads the keychain token, and its offline snapshot is filed under that token. `connect` runs only after a sign-out has reset the account. The share, widget and notification extensions hold no token.
- Writes from outside the app's screens name their account. A notification's Decline sends the account it was delivered to, and the server refuses it for anyone else. A Live Activity's Stop runs only when the signed-in scope matches its own. Siri and notification replies join drafts under a scope.
- Voice clips are stored under a path made from the token, and the composer drops a recording when that path changes. Read markers are the `read-position` write above. Pending sends and queued uploads are cleared by `resetAccountContent`.
- Presence is not covered. The 15 second presence beat in `AppStore+Presence.swift` reads the current client on each beat and has no `generation` check, so a beat in the gap reports "active" for the chat on screen under the new token. It carries no content of member one's, and the chat view leaves once the account clears, which stops it. It is left as it was.

## Item 3: a card fence inside a list item

The web renders a card where Markdown puts its code block, but only for a card whose fence `replyCardsFromText` finds, and that regex wants the fence at the margin. The server checks card IDs with the same function. A card fence indented inside a list item is therefore code inside that item on the web, and the list stays whole. iOS took any fence indented up to three spaces as a card, so the card came out of the list and split it. On `af8d1c38` the parts were the list's first two items, the card, then `3. Close the gate.` (`red.log`). iOS now matches the web. The web shows such a card as code rather than as a card, which is the defect that remains on both clients. iOS still lifts a `wildbots-html` fence out of a list item, where the web renders it in place, and still takes tilde and four-backtick card fences that the server does not. Neither is changed here.
