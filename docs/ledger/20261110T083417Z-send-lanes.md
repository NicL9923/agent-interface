## Change

- `route` queues `agent-interface.submit` on a send lane per assistant (`LaneQueue`, the read queue
  generalized, four workers), the way it already queues opens and discovery. The reader goes on reading.
- `submit` stops a background compaction before `submission_lock`, under `IdleCompaction.admitting(sid)`,
  then preempts again under the lock with what remains of the 30-second bound.
- `journal.lock` covers each journal transaction in `admit` and nothing else: never image staging, never
  Hermes's `prompt.submit` or `session.steer`. `submission_lock` still spans the whole admission.
- A fresh admission's answer carries `app_timing`: `queued`, `open`, `preempt`, `wait`, `journal`,
  `staging`, `native`, `total`, in milliseconds. A replay answers what was saved, without timings.
- A profile that is not a string gets its handler's error from a lane of its own. Before, a list or object
  profile made `route` raise `TypeError` for an open.

## Native behavior relied on, read from upstream `ed1afb082eb3`

ledgers cite. It is not necessarily the production revision.

  caller's context copied, so the bound transport goes with them (`tui_gateway/rpc_dispatch.py:75`, `:87`).
  `session.steer` calls `agent.steer` from whichever thread serves the request, never the turn's own
  (`tui_gateway/methods_session_interrupt.py:114-130`, `:171`). Native `image.attach` runs inline on the

- The caller's transport: `prompt.submit` rebinds the session to `current_transport()`
  (`methods_prompt.py:887-888`). The lane binds the caller's transport before it runs, as the read lane
  does. A late request from a socket that closed meanwhile is handled natively: the rebind re-arms the

- Fences: native `handle_request` reserves retirement admission for each call (`rpc_dispatch.py:8-14`) and

## Invariants and how each still holds

- One owner per request ID, and the digest check. Every receipt insert is in `admit` (also checked: the
  only `INSERT INTO receipts` statements in `src/hermes`), which runs under `submission_lock` and reads the
  request ID, compares the digest and inserts within that one hold. Goal continuation calls `submit` with the
  lock already held. The early read outside the lock only skips the preempt and canonical open for a known
  request ID; the decision is made again under the lock. Test: a duplicate on the same lane and from another
  connection gets the saved answer and Hermes is called once; the same request ID sent to another assistant
  while the first is inside Hermes's call, so on another lane, gets 4093 and changes nothing. Answering a
  replay from the early read instead goes red.
- Interruption review. `interruptions` rows are written only when the journal opens at startup and deleted
  only in `admit`, so the read under `submission_lock` holds until the delete.
- The receipt row exists before any frame of its turn. The FULL-synchronous intent insert commits before
  Hermes is called, on the same thread; Hermes starts the turn thread inside that call. Test: while Hermes's
  call is held, the turn's `app_prompt` reads the intent row and a tool frame is recorded under its run.
- No settlement, delivery or compaction interleaves with an admission. `followups`, `delivery_admission` and
  `compact` take `submission_lock`, which still spans staging and Hermes's call. Test: a routine delivery
  to the same chat waits until the staging send is answered.
- No compaction starts between the first preempt and the lock. `compact` registers its attempt under
  `IdleCompaction.lock` only while no hold is taken, and `admitting` takes the hold under the same lock:
  either the attempt registered first and the preempt after the hold finds it, or it never starts. A
  timestamp touch would not do: the delay can be shorter than the 30-second preempt bound (four seconds in
  the qualification probe). Test in `tests/hermes_compaction_test.py`.
- Maintenance and retirement. A queued send reserves admission in `route` before it is queued and releases
  it once answered, as a read does. A lease request is refused with 409 "Hermes still has active work" while
  a send runs or waits, and a send under a held lease is refused 409 before it reaches a lane, as before. A
  retiring gateway refuses a send with 5035 at arrival, before any receipt.
- A native call that raises releases every lock through `with` blocks, and the lane answers the caller even
  when the handler itself raises (-32000).

## Decisions

- `submission_lock` stays global and keeps image staging and Hermes's call inside it. Staging outside it
  would let a routine delivery's turn (`delivery_admission`, `bot_delivery`) take the staged images, and
  `followups` could settle the new uncertain receipt with another turn's outcome before Hermes admitted it.
  A lock per assistant would change goal continuation, compaction and delivery, which all rely on one global
  lock, and their lock order. So a send to one assistant held in staging still delays a send to another by
  the staging time, which natively is a path resolution and an image header read. The 30-second preempt,
  the long wait, no longer does.
- Four send workers. Only the preempt waits long, and the idle compactor runs one compaction at a time, so
  at most one lane at a time waits on one.
- Timing goes on the live answer, not in the saved admission response, so a replay never reports the
  original call's timings as its own. Node passes any lowercase phase name; no Node change on this branch.
- Visible change: an open, a receipt lookup or a tool frame during an admission now proceeds and sees the
  intent row, `uncertain`, and an open names its run as `app_run_id` before Hermes answers. That row is the
  admission's durable state, the same one a crash at that moment leaves. If Hermes then refuses, the next
  open shows no run. Before, those readers waited on `journal.lock` until the admission finished.
- Maintenance on the same socket as a running send used to be read only after the send finished. It is now
  read at once and refused as active work.
