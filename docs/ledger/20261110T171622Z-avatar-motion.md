## The avatar's renders: measured, not changed

`src/components/Avatar.tsx:338` runs each animated avatar on the shared frame loop in
`src/components/avatar-frames.ts`. `advance` moves a ref-held clock without React, and `commit` calls
`setFrame` (`Avatar.tsx:371`). The loop commits every awake avatar in one `flushSync` per frame. Avatars under
56 px sleep 24 ms between frames, so they repaint at about 30 fps. The SVG's geometry (eyes, trails, squash,
props) is computed in render from the pose, so React writes the changed attributes.

A one-off script, not kept, ran a Trail Cook "Echo:" turn that stays thinking on `e2e/server.ts`, in Chromium
1280 x 800. It observed every avatar SVG for 10 s and read `Performance.getMetrics`. It counted animation frames
that carried any avatar write. Two avatars animate: the 42 px header avatar and the 52 px activity row avatar.

| Build | Frames with avatar commits per second | Script ms/s | Style ms/s | Layout ms/s | Task ms/s |
| --- | --- | --- | --- | --- | --- |
| `main`, motion allowed, 3 runs | 29.6, 30, 30 | 24.4, 14.8, 14.4 | 37.2, 20.8, 19.6 | 8.6, 6.0, 5.6 | 148, 84, 80 |
| `main`, reduced motion | 0 | 0.9 to 1.9 | 0 | 0 | 8.6 to 14.1 |

Other worktrees were running suites on the same machine, so the per-second costs vary between runs. A CPU profile at
100 µs sampling over 10 s put 50 to 66 ms in the React bundle and 34 to 45 ms in the avatar's own module, its pose
math and render, with `setAttribute` at 23 ms. React's share is about 5 to 7 ms a second, under 1% of one core.
Driving the SVG from a ref would remove that share. The pose math, the attribute writes, the style recalculation and
the layout would all stay, because the same attributes still change 30 times a second. That would mean rewriting the
760-line render as imperative DOM writes, at real risk of drawing the avatar differently. Not worth it on these
numbers, so not done.

A first count showed 60 commits a second. That was two observers each reporting the same commit. A change that put
sleeping avatars on a shared wake, so two out of step would commit together, was measured at 30 frames a second, the
same as `main`: here both avatars start in the same commit and are already in step. It was reverted.

## Review fix round: Grok 4.7's finding on the keyframe test

Grok 4.7 found that `tests/css-keyframes.test.ts` stayed green with the 380 ms `animation` restored on
`.message-outgoing`, pinned `used.length > 20`, and would fail on an easing or keyword its stop list did not know.

The test now reads each stylesheet with a small block scanner, so every declaration knows its file, line, selector
list and the at-rules around it. It asserts:

- Each keyframe name is defined once (unchanged).
- Each animation layer names a defined keyframe. Durations, easings and keywords in the layer are ignored, so an
  unknown keyword cannot fail it; `none`, CSS-wide keywords and a layer that is only `var(...)` are left alone.
  Layers are split on top-level commas only, so `cubic-bezier(0.2, 0.9, 0.3, 1.15)` stays in one layer. No count.
- No selector gets an animation, other than `none`, from more than one rule under the same motion setting. A rule
  outside `prefers-reduced-motion` counts for both settings; width, container and supports conditions are part of
  the context, so a narrow-screen variant is not a second rule.
- `.message-outgoing` has one `animation` declaration, `message-send`, inside `prefers-reduced-motion: no-preference`.

The duplicate check found a base rule and a `src/motion.css` spring on four more selectors, each with a
reduced-motion `none`: `.bot-menu` (`src/app/home.css:318`), `.dock-item` (`src/app/shell.css:149`), `.toast`
